# Entries dashboard: project-management widget assessment

**Date:** 2026-10-31
**Status:** Dashboard and sidebar prototype implemented; awaiting visual review
**Scope:** Core Entries defaults for both NOMAD Central and individual Oases

## Decision at this review gate

Remove the app-overview widget. It duplicates the Apps page and does not explain the
data or the state of scientific work.

Do not label any existing metadata widget as a project-status, sample, or processing
view. Core NOMAD already models entities, activities, processes, measurements, and
their references in archive data, but it does not yet expose a clean, domain-neutral
search summary for those concepts. The useful immediate prototype is therefore a
pair of complementary workflow/method widgets plus recency and dataset context. A
real sample/process/status dashboard requires a small results-model and normalization
extension first.

The recommended configuration-only prototype was approved and implemented on
2026-10-31. It replaces the comparison widgets with Simulation workflows,
Experimental methods/activities, Data added to NOMAD, and Datasets/collections.
This is the first step of the combined approach; the results-model extension remains
a separate review phase.

## Product direction from the workflow deck

The reference deck is
`/Users/jfrudzinski/Downloads/Inter_area_Using_NOMAD_in_Everyday_Scientific_Workflows.pptx`.
The relevant message is not “browse software features”; it is “understand and manage
the work”:

- everyday work connects samples, instruments, results, analyses, and simulations;
- the lifecycle is plan, synthesize, prepare/process, measure, analyze, compare with
  simulation, and publish;
- a project is presented as a shared container, an entry as a sample/measurement/
  calculation, and a reference as the link between them;
- present projects store results, but do not adequately show sample inventory,
  location, next work, or status such as waiting/running/done;
- the desired views are explicitly sample/process browsing, a plan view, and a
  status board;
- the XPS Oasis example uses separate apps for calibrations, experiments, and plans.

This supports a generic Entries dashboard that summarizes scientific objects and
workflows. It also supports later context-specific “Work” or “Projects” apps for
Oases; it does not support duplicating the Apps directory inside Entries.

## What core metainfo already provides

### Archive-level concepts

The base sections in `nomad/datamodel/metainfo/basesections/v1.py` and `v2.py`
already contain much of the right scientific model:

| Concept | Current core representation | Important fields/links |
| --- | --- | --- |
| Generic record | `BaseSection` | `name`, `datetime`, `lab_id`, `description` |
| Persistent thing | `Entity` | creation time and stable identity |
| Scientific action | `Activity` | start/end time, `method`, `location`, ordered steps |
| Sample/material object | `System` | entity semantics and composition/system data |
| Equipment | `Instrument` | entity semantics and references from activities |
| Material transformation | `Process` | samples, instruments, outputs, steps |
| Observation | `Measurement` | samples, instruments, result outputs |
| Grouping | `Experiment`, `Collection` | activities or entities |
| Workflow graph | `workflow2` | tasks plus input/output links generated by normalizers |

This is a strong basis for project-oriented views. The missing layer is a compact,
stable search summary derived from it.

### Searchable summaries available today

`nomad/datamodel/results.py` exposes these aggregatable fields:

| Search quantity | What it actually means | Fitness for a default widget |
| --- | --- | --- |
| `results.method.workflow_name` | Workflow name produced by the method/results normalizers | Useful for simulations; not a cross-domain workflow type |
| `results.eln.methods` | Explicit activity method, or the activity section-definition name | Semantically promising for experiment/Oasis use, but free-form and sparse on Central |
| `results.eln.instruments` | Instrument names collected by ELN normalization | Useful in a lab Oasis; too sparse and high-cardinality for Central |
| `results.eln.sections` | Names of all encountered ELN section definitions | Too noisy: includes nested and schema-internal section names |
| `results.eln.lab_ids` | Lab-specific identifiers | Good lookup/link key; poor distribution widget |
| `results.eln.tags` | User-defined tags | Flexible but uncontrolled and currently very sparse |
| `datasets.dataset_name` | User-curated publication/catalog grouping | Useful context, but not equivalent to an active project |
| `upload_create_time` | NOMAD ingestion time | Reliable recency view, but not scientific activity time |
| `process_status` | NOMAD ingestion/processing pipeline status | Must not be presented as experiment or project status |
| `published` | Repository publication state | Useful for private/Oasis work; nearly constant for anonymous Central |

`Activity.datetime`, `Activity.datetime_end`, `location`, the semantic base class of
the top-level section, and the workflow input/output relationships remain in archive
data. They are not normalized into generic aggregatable results fields. Likewise,
there is no core indexed project/campaign name or scientific work-status vocabulary.

## Evidence from public staging data

An unauthenticated terms-aggregation probe was run against the staging Entries API
with owner scope `visible` on 2026-10-31. The response contained 19,456,010 visible
entries. Counts below are the leading returned buckets, not a claim that every entry
with a field is represented by those buckets. Multi-valued fields can count one entry
in more than one bucket.

| Candidate | Observed leading buckets | Assessment |
| --- | --- | --- |
| Workflow name | `GeometryOptimization` 4,016,848; `SinglePoint` 2,632,925; `single_point` 580,965; `geometry_optimization` 107,517 | Strong Central presence, but simulation-dominated and split by casing/naming variants. The returned buckets cover about 37.9% of all visible entries. |
| ELN methods | `Generic Experiment` 9,001; `CatalyticReaction` 2,150; all other leading values much smaller | Meaningful on experiment-focused Oases, but the returned buckets total only about 0.058% of Central staging. Values mix method labels and schema type fallbacks. |
| ELN sections | `Root` 9,015 followed by schema-internal names such as `Em__ENTRY__...` | Not acceptable as a user-facing sample/process classifier. Nested section definitions dominate the facet. |
| Instruments | Largest bucket 750; many verbose make/model strings | Valuable operationally in a local lab, but sparse and fragmented globally. |
| Tags | `project` 4; most leading values 1–2 | Not mature enough for a default widget. |
| Datasets | `Alexandria PBE` 4,048,368; `Alexandria PBEsol` 1,906,323 | Useful catalog context, but dominated by large imported databases and not a progress view. |
| Entry type | `VASP GeometryOptimization` 3,959,600; `VASP DFT SinglePoint` 2,460,373 | Confirms the volume bias that motivated this redesign. It mixes program, method, workflow, and schema concepts. |
| Published | true 19,419,808; false 36,202 | Almost constant for anonymous Central and therefore uninformative there. |

The staging evidence explains why one universal configuration is difficult: Central
is a very large public repository dominated by imported simulation collections,
whereas an Oasis can contain private plans, lab samples, instruments, and current
work. A field can be semantically right for an Oasis and still look empty on Central.

## Candidate widgets

### Configuration-only options available now

| Widget | Quantity | Central | Oasis | Recommendation |
| --- | --- | --- | --- | --- |
| Simulation workflows | `results.method.workflow_name` | Useful, but biased and naming variants need cleanup | Useful where simulations are present | Prototype now, with the honest title **Simulation workflows** rather than **Workflows** |
| Experimental methods and activities | `results.eln.methods` | Very sparse, but shows the experimental side | Potentially useful and locally meaningful | Prototype now beside simulation workflows; do not interpret it as complete activity classification |
| Data added over time | `upload_create_time` | Useful | Useful | Keep, but say **added to NOMAD**, not activity/progress time |
| Datasets / collections | `datasets.dataset_name` | Useful catalog view, strongly skewed by large databases | Can approximate a project only where local practice uses datasets that way | Keep as secondary context, not as the primary project widget |
| Instruments | `results.eln.instruments` | Too sparse | Useful in instrument-centered labs | Oasis-specific candidate, not universal default |
| Access/publication state | `published` or visibility control | Almost constant when signed out | Useful to a signed-in Oasis user | Context-specific control, not universal dashboard tile |
| Entry types | `entry_type` | Strong but volume-biased | Schema/program-dependent | Remove from the intended final dashboard after comparison review |
| External databases | `external_db` | Provenance/catalog context | Usually sparse | Secondary metadata, not project management |

The best no-model-change prototype is therefore:

```text
┌──────────────────────────┬─────────────────────────────────┐
│ Simulation workflows     │ Experimental methods/activities │
│ workflow_name            │ results.eln.methods             │
├──────────────────────────┼─────────────────────────────────┤
│ Data added to NOMAD      │ Datasets / collections          │
│ upload_create_time       │ datasets.dataset_name           │
└──────────────────────────┴─────────────────────────────────┘
```

This intentionally shows the asymmetry between Central and Oasis data rather than
claiming to solve it. It is a better visual prototype than entry types, but still not
a project-management dashboard.

### High-value widgets that need normalized fields

| Desired widget | Proposed normalized search concept | Why it matters |
| --- | --- | --- |
| Records by scientific role | controlled `entity_type` and `activity_type` derived from base-section inheritance | Separates sample/system, instrument, collection, process, measurement, experiment, analysis, and simulation without exposing schema class names |
| Work status board | scientific lifecycle status such as planned, ready/waiting, in progress, completed, failed/cancelled | Implements the deck's plan/running/waiting/done view; distinct from parser `process_status` |
| Scientific activity timeline | normalized activity start/end time | Shows when work happened or is planned, rather than when it was uploaded |
| Samples and processing | normalized counts/types for input samples, output samples/results, and linked process/measurement/simulation records | Supports sample history and process-chain browsing |
| Project/campaign overview | stable project/campaign identifier, name, and optional status | Makes shared work units explicit instead of overloading uploads or publication datasets |
| Instrument workload | normalized instrument identity/type plus activity time/status | Useful for Oasis scheduling and operational review |

The semantic type fields should be derived from inheritance or explicit controlled
annotations, not `m_def.name`. Otherwise custom schemas will recreate the current
`results.eln.sections` noise. Human names should stay separate from controlled types.

## Recommended product split

### Generic Entries app, now

- Keep broad cross-domain search and generic columns.
- Use the configuration-only four-widget prototype above for the next visual review.
- Treat dataset and upload time as repository context, not scientific progress.
- Do not add app navigation back into the dashboard.

### Generic results-model extension, next

1. Add controlled entity/activity roles derived from `Entity`, `System`, `Instrument`,
   `Collection`, `Activity`, `Process`, `Measurement`, and `Experiment` inheritance.
2. Add scientific activity start/end summaries.
3. Design a scientific lifecycle status separately from processing status.
4. Add normalized relationship summaries for input/output entities and linked
   activities. Preserve the detailed references in `workflow2`.
5. Validate normalization against both core base-section versions and custom schemas,
   including reprocessing behavior and idempotency.

### Context-specific apps, later

- A Central-facing catalog/exploration app can emphasize public datasets,
  provenance, workflows, and publication time.
- An Oasis-facing Work/Projects app can emphasize plans, sample inventory,
  instrument workload, unpublished/shared data, and status boards.
- Domain apps such as XPS Plans, Experiments, and Calibrations can remain curated
  slices of those normalized concepts.

This avoids forcing one dashboard to pretend that an anonymous public repository and
an authenticated working lab have the same management needs.

## Sidebar expansion after dashboard review

The first dashboard review showed that the generalized Entries app also needs enough
curated filters to explain and navigate the heterogeneous result set. The approved
prototype therefore borrows only the highest-level concepts from the Calculations
and NeXus apps instead of copying either app's complete domain-specific menu.

The implemented order is:

1. **Material** — periodic table, Hill formula, structural type, and crystal system.
2. **Method / activity** — a controlled list of normalized methods plus the dynamic
   ELN method/activity facet.
3. **Workflow** — a controlled list of the main supported simulation workflows:
   Single point, Geometry optimization, Molecular dynamics, Phonon, Elastic,
   Equation of state, and Thermodynamics.
4. **Properties** — the high-level electronic, vibrational, and mechanical property
   availability filters from Calculations, without copying the detailed numerical
   subfilters.
5. **Instruments** — the portable `results.eln.instruments` summary rather than
   NeXus-schema-specific instrument paths.
6. **NeXus** — only the NeXus class filter.
7. **Entry / Schema**, **Author / Origin / Dataset**, and **Visibility / IDs** — the
   existing generic metadata groups.

`entry_type` remains under Entry / Schema. It is not labeled as a method because it
mixes schema, program, method, and workflow concepts. Method searches instead use
`results.method.method_name` and `results.eln.methods`.

The Workflow section uses `results.method.workflow_name` internally because core
results currently has no separate normalized workflow-type quantity. Supplying a
fixed canonical option list avoids presenting arbitrary names and malformed legacy
values as supported workflow types. A future `workflow_type` result field would be a
cleaner replacement.

The NeXus class path is optional metainfo. Its configuration includes the explicit
`#str` datatype suffix, which lets the generic app validate when pynxtools is not
installed. The new GUI then creates a typed filter definition locally. On an Oasis
without NeXus data the filter is empty; against Central staging it aggregates the
dynamic NeXus field normally.

A staging probe over 9,024 visible NeXus entries confirmed that `entry_type` and
NeXus class are closely related but not identical presentation fields: leading entry
types were human-readable labels such as `Em Experiment`, while the class facet used
canonical values such as `NXem`. This supports keeping both, but only exposing the
canonical class inside the NeXus section.

## Implementation status and next review

The three considered scopes were:

1. **Prototype-first:** replace the four current comparison widgets with Simulation
   workflows, Experimental methods/activities, Data added to NOMAD, and Datasets /
   collections. This is configuration-only and can be reviewed immediately against
   staging data.
2. **Model-first:** keep the current baseline temporarily and first add controlled
   entity/activity types plus scientific dates. This takes longer but enables honest
   Samples, Processes, and Measurements widgets.
3. **Combined:** build the configuration-only prototype now, then treat controlled
   roles/status/relations as the following separately reviewed phase.

The **Combined** choice was approved. The configuration-only part is now implemented.
The next review should inspect the four widgets with both Central staging data and,
if possible, a representative Oasis dataset. In particular, check whether the sparse
experimental widget still communicates useful breadth and whether dataset names add
enough project context to justify their place.

Implementation verification on 2026-10-31:

- the focused UI-model and apps-router suite passed all 52 tests;
- Ruff and Git whitespace checks passed;
- the restarted local backend returned the four widget titles and quantities shown
  above from `/api/v1/apps/entry-points/entries`;
- all four referenced quantities were present in the endpoint's `search_quantities`
  map.

Do not start the results-model part until that visual review is accepted. That part
will add controlled roles/status/relations rather than further stretching existing
metadata fields.

For the model phase, the main open decision is whether project and lifecycle status
belong in core metainfo for all entries or in a dedicated Oasis Work/Projects model
that references ordinary entries. That should be settled before naming or indexing
new fields.
